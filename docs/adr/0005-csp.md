# 0005 — Content Security Policy

- Statut : accepté
- Date : 2026-11-04 (plan, section Sécurité : test de la CSP prévu en phase 1)

## Contexte

Le plan visait une CSP stricte, sans `'unsafe-inline'` pour les scripts, tout en gardant des pages publiques générées au build et servies par le CDN. Deux pistes étaient à tester en phase 1 : le hachage via `experimental.sri` sur les pages statiques, et le nonce sur `/admin`, que la documentation Next.js juge incompatible avec le pré-rendu partiel.

## Tests réalisés

Build de production Next.js 16.4.5, `next start`, page chargée dans Chromium avec un écouteur `securitypolicyviolation`.

| Variante                                                                                                      | Résultat                                                                                                                                                                                                               |
| ------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pages publiques : `script-src 'self'` et `experimental.sri`, comme dans l'exemple de la documentation Next.js | Échec : 11 scripts en ligne bloqués (les données React Server Components intégrées à la page). Le HTML s'affiche mais la page n'est pas hydratée. Un des 7 fichiers JS n'a d'ailleurs pas reçu d'attribut `integrity`. |
| Pages publiques : `script-src 'self' 'unsafe-inline'`, sans SRI                                               | Réussite : aucune violation, page hydratée.                                                                                                                                                                            |
| `/admin` : nonce et `'strict-dynamic'` posés par `proxy.ts`, page en pré-rendu partiel                        | Échec : 8 violations, les scripts de la coque statique, générée au build, n'ont pas de nonce.                                                                                                                          |
| `/admin` : même CSP, page rendue à chaque requête (`export const instant = false` et `await connection()`)    | Réussite : tous les scripts portent le nonce, aucune violation, page hydratée.                                                                                                                                         |

## Décision

- **Pages publiques** : `script-src 'self' 'unsafe-inline'` ; `style-src 'self'` tant qu'aucun style en ligne n'est nécessaire. Les autres directives restent strictes : `default-src 'self'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'none'`, `upgrade-insecure-requests` sur Vercel.
- **SRI abandonné** : la fonction est expérimentale et n'apporte rien à la CSP une fois `'unsafe-inline'` présent ; les scripts sont servis par la même origine.
- **Admin (phase 7)** : CSP à nonce et `'strict-dynamic'` générée par `proxy.ts`, pages de l'admin rendues à chaque requête (`instant = false`), et l'en-tête CSP des pages publiques exclu de `/admin`.
- **Aperçus Vercel** : la barre d'outils Vercel est autorisée sur les aperçus uniquement.
- **Développement** : `'unsafe-eval'` et les styles en ligne autorisés, jamais en production (vérifié par un test e2e).

## Conséquences

- Note Mozilla Observatory attendue : B+ au mieux, à cause de `'unsafe-inline'` ; le plan l'avait prévu.
- Le risque est faible sur le site public : pages statiques, aucun contenu saisi par un visiteur n'y est affiché, Markdown assaini (rehype-sanitize), aucun script tiers.
- L'admin, seule partie qui manipule des secrets et des données saisies, garde la CSP la plus stricte.
- Si une image floue de `next/image` ou un autre composant pose des styles en ligne, `style-src` devra s'assouplir : à vérifier au moment de l'ajout.

## Alternatives écartées

- Hachages calculés après le build et injectés par route : il faudrait deux builds identiques ou un `proxy.ts` sur chaque page publique, donc plus de complexité et des pages qui ne sont plus servies directement par le CDN.
- Nonce sur tout le site : toutes les pages deviendraient dynamiques, sans cache CDN ni pré-rendu, à l'encontre des objectifs de performance.

## À revoir

Quand Next.js saura hacher les scripts en ligne des pages statiques, ou couvrir ces scripts par SRI, revenir à une CSP sans `'unsafe-inline'`.
